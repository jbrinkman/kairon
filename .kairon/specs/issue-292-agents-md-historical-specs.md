# Issue #292: Add AGENTS.md guidance: don't edit historical .kairon/specs in review

Closes #292

## Problem

Review agents (CodeRabbit, Copilot, our `code-review` skill) propose edits to files under `.kairon/specs/`.
Those files are architect point-in-time design specs: each records what the architect decided for one issue at
one moment and is never maintained afterwards. On PR #291 two review comments asked to edit
`.kairon/specs/issue-290-skip-sandbox-tests-no-container-daemon.md`. Nothing in the repo tells an agent that
this is wrong (no `AGENTS.md`, no `.kiro/steering/`), so each such comment costs a human a triage round, and an
agent that "fixes" it rewrites history.

## Findings from codebase investigation

Verified in the worktree (`git ls-files`, `.gitignore`, `Taskfile.yml`, `.releaserc.json`):

- No `AGENTS.md`, `CLAUDE.md`, `.coderabbit.yaml`, copilot instructions, or `.kiro/steering/` exist in the repo.
- `.kairon/specs/` is tracked: ~120 files (`issue-<n>-<slug>.md`, a few `tui-refactoring-*.md`,
  `validator-test-scenario-242.md`, `github-polling-optimization.md`, and a `maturity-model/` subdirectory with
  `.md` and `.png`). Everything in the tree is historical. README.md line 166 documents the architect writing
  `.kairon/specs/issue-<number>-<slug>.md`.
- `.kairon/evals/` is **mixed**: `cases/`, `fixtures/`, `rubrics/` are live, maintained, and template-synced
  (`task sync:check`); `results/` is tracked generated run output (18 timestamped run dirs, ~49 json files),
  explicitly excluded from the sync check (`--exclude=results`).
- `CHANGELOG.md` is generated by `@semantic-release/changelog` (`.releaserc.json`); hand edits are overwritten or
  conflict on the next release.
- `.kairon/validation-results.md` (Issue #107) and root `VALIDATION_SUMMARY.md` (an old "Task 6" report) are
  tracked one-off validation snapshots from past issues, in the same category as specs.
- `.gitignore` already excludes `app_docs/` (documenter output), `.kairon/retries/`, `.kairon/artifacts/`,
  `.kairon/sessions/`, `.kairon/sentinels/`. These never appear in a PR diff, so a reviewer cannot comment on them.
- Template sync (`builder-conventions`) covers `.kiro/agents`, `.kairon/scripts|themes|evals`, and the
  `sentinel-protocol` skill. `AGENTS.md` is a repo-specific contributor/agent policy, not an artifact deployed by
  `kairon init`, so it is **not** added to `cmd/kairon/templates/` and `task sync:check` is unaffected.
- Pre-existing uncommitted modifications to `.kiro/agents/*.json` are unrelated. **Do not touch, stage, or revert
  them.**

## Solution Approach

Add a single new file, repo-root `AGENTS.md`, as the one place that states which paths are immutable
historical/generated artifacts and what to do when a review comment targets one. `AGENTS.md` is the de-facto
cross-tool convention (Kiro steering, Copilot, and other review/coding agents read it from the repo root), so no
tool-specific configuration is needed. This is best-effort guidance for agents, not an enforcement mechanism
(enforcement such as CODEOWNERS or CI path guards is out of scope).

### Design decisions

1. **Explicit allow-list of frozen paths, not a blanket markdown freeze** (AC 3). The frozen set is named
   path-by-path. The file states that everything not listed, including README, CONTRIBUTING, `docs/`, agent
   prompts, skills, scripts, code and tests, is live and freely editable.
2. **Frozen set (final decision):**
   | Path | Category | Rationale |
   |------|----------|-----------|
   | `.kairon/specs/` (whole tree, incl. `maturity-model/`) | Historical design specs | Point-in-time architect output; the issue's primary target |
   | `.kairon/evals/results/` | Generated eval run output | Timestamped results; regenerated by `kairon eval`, never hand-edited |
   | `.kairon/validation-results.md`, `VALIDATION_SUMMARY.md` | Historical validation snapshots | One-off reports from past issues (#107 and earlier); same failure mode as specs |
   | `CHANGELOG.md` | Generated | Owned by semantic-release; fix via commit messages or `.releaserc.json` |
3. **Judgement calls on the candidates named in the issue:**
   - `app_docs/` and `.kairon/retries/` are **not** listed as immutable trees. They are gitignored runtime output
     and can never be the target of a review comment. Listing them as "immutable" would be inaccurate for
     `app_docs/` (documenter legitimately rewrites it locally) and noisy. Instead a short "untracked runtime
     output" note says: do not commit them, and they are not review targets. (`.kairon/artifacts/`,
     `.kairon/sessions/` get the same one-line treatment for completeness.)
   - `.kairon/evals/` as a whole is **not** frozen; only `results/` is. `cases/`, `fixtures/`, `rubrics/` are
     maintained and template-synced, and the file says so to avoid over-freezing.
4. **Reject-and-redirect procedure** (AC 2), in a section titled "Historical artifacts":
   1. Do not edit the file to satisfy the comment.
   2. Reply (or resolve) noting the file is a historical point-in-time artifact that is intentionally not updated.
   3. Judge the underlying concern on its merits. If valid (a real bug, wrong behaviour, missing test, stale
      user-facing doc), apply the fix to the live artifact (code, tests, README/docs, live agent prompts/skills)
      instead. If the concern only concerns the spec's own wording (typo, formatting, "spec says X but code
      does Y" where the code is right), decline with no change.
   4. Provide a copy-paste reply template, with the PR #291 / issue-290 spec as the worked example.
5. **Carve-outs so the pipeline is not broken:** the architect agent creating (or, on a retry, overwriting) the
   spec file for the issue it is currently processing (`.kairon/specs/issue-<n>-<slug>.md`) is normal pipeline
   output, as is any edit a maintainer explicitly requests. The rule targets edits made *in response to review
   feedback on existing historical files*.
6. **No duplicated guidance elsewhere.** Issue scope excludes changing the `code-review`/`pr-comment-resolver`
   skills, third-party bot config, and existing spec files. README and CONTRIBUTING are left unchanged; the
   existing README line 166 remains accurate.

### Proposed `AGENTS.md` content (builder: use this as the baseline; wording may be polished but every
### required element below must remain)

````markdown
# AGENTS.md

Guidance for AI agents (coding, review, and comment-resolution agents) working in this repository.
Humans are welcome to read it too.

Most of this repository is live and should be edited freely to fix bugs and address review feedback: Go code,
tests, `README.md`, `CONTRIBUTING.md`, `docs/`, agent prompts, skills, scripts and templates. A small, explicitly
listed set of paths is **not** live. Those are described below. Markdown is **not** frozen as a category; only the
paths named in this file are.

## Historical artifacts (do not edit)

These paths are point-in-time records or generated output. Do **not** edit them to address review feedback,
lint findings, or "stale content" observations.

| Path | What it is | Why it is not edited |
|------|------------|----------------------|
| `.kairon/specs/` (entire tree, including `maturity-model/`) | Architect design specs: one per issue, written when the issue was processed | They record the design as decided at that time. Later code legitimately diverges; that is not a defect. |
| `.kairon/evals/results/` | Generated eval run output (timestamped directories) | Produced by `kairon eval`; regenerated, never hand-edited. |
| `.kairon/validation-results.md`, `VALIDATION_SUMMARY.md` | One-off validation reports from past issues | Snapshots of a past run. |
| `CHANGELOG.md` | Release changelog | Generated by semantic-release from commit messages; hand edits are overwritten. Fix the commit message or `.releaserc.json` instead. |

Untracked runtime output (`app_docs/`, `.kairon/retries/`, `.kairon/artifacts/`, `.kairon/sessions/`) is
gitignored. Never commit it; it is not a review target.

### When a review comment targets a historical artifact

1. **Reject the edit.** Do not change the file.
2. **Say why.** Reply that the file is a historical, point-in-time artifact and is intentionally left as written.
3. **Redirect the concern.** Decide whether the underlying concern is valid on its own merits. If it is, apply
   the fix to the **live** artifact instead: the code, the tests, `README.md` / `docs/`, or the live agent
   prompt or skill. If the concern is only about the historical file's own wording, decline with no change.
4. Resolve the thread.

Suggested reply:

> `.kairon/specs/` holds point-in-time architect design specs and is intentionally not edited after the fact.
> I have not changed this file. The underlying concern is valid, so I fixed it in `<live file>` instead
> (`<commit>`). / The concern only affects the historical wording, so no change is needed.

Example: on PR #291, review comments asked to edit
`.kairon/specs/issue-290-skip-sandbox-tests-no-container-daemon.md`. The correct response is to leave that spec
alone and, if the point was valid, change the code or test that the spec describes.

### Exceptions

- The architect agent writing (or, on retry, rewriting) the spec for the issue currently being processed,
  `.kairon/specs/issue-<number>-<slug>.md`, is normal pipeline output and is allowed.
- A maintainer explicitly asking for a specific edit to one of these paths.

## Live documentation and code (edit freely)

Everything not listed above is maintained and should be updated when it is wrong or stale, including in response
to review comments:

- `README.md`, `CONTRIBUTING.md`, `docs/`
- Go code and tests under `cmd/` and `internal/`
- `.kiro/agents/`, `.kiro/skills/`, `.kairon/scripts/`, `.kairon/themes/`, `.kairon/config.yaml`
- `.kairon/evals/cases/`, `.kairon/evals/fixtures/`, `.kairon/evals/rubrics/`

Template-synchronized files (see `.kiro/skills/builder-conventions/SKILL.md`) must be re-synced into
`cmd/kairon/templates/` and verified with `task sync:check` after editing.
````

## Risks and Notes

- Guidance only: tools are not forced to honour `AGENTS.md`. Acceptable per the issue; enforcement is out of scope.
- Over-freezing risk mitigated by an explicit allow-list and the "edit freely" section.
- The frozen list adds `.kairon/evals/results/`, the two validation snapshots and `CHANGELOG.md` beyond the issue's
  single named candidate. These are the same failure mode (generated/historical, tracked, reviewable). If a
  maintainer prefers only `.kairon/specs/`, trimming rows from the table is a trivial change.
