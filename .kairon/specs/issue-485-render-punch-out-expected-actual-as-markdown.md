## Solution Approach

### What is wrong today

`RenderComment` (`internal/failure/render.go`) calls `fenced()` for Expected, Actual and the default remedy's copy of Expected. GitHub does not wrap code blocks, so a one-paragraph value is one long line. These values are prose or Go error strings, so they should be Markdown text.

### Chosen design

Replace the `fenced(...)` calls for Expected, Actual and the default remedy with one new function, `renderValue(s string) string`. It returns Markdown text that ends with a newline. `fenced()` stays as the helper for preformatted text. Everything else in `RenderComment` stays byte-for-byte the same: the marker line, the bold intro line, the stage/guard/attempts list, the `**Expected**` / `**Actual**` / `**Remedy**` headings, a caller-supplied remedy (still truncated and written raw), and the restart line.

The package stays pure Go. It may import only the standard library (`strings`, `unicode`, `unicode/utf8` and similar), `internal/guard`, `internal/stageoutput` and `internal/config`, and must not import `os`, `os/exec`, `net` or `net/http` (`TestNoForbiddenImports` checks the non-test imports from `go list`). No new dependency is needed.

Design principle: the output is Markdown that Kairon fully controls. Every construct that could act (mention, reference, link, image, HTML, a backtick that could pair with a wrapper) is neutralized, and every character the renderer would consume (backslash, backtick, and a `[` that could open link text) is escaped so the text shows as typed. The value's own formatting (bold, lists, a code fence) is allowed to work, because the issue says "The value is Markdown text".

Safety invariant for links (this is what the rules below guarantee): in the rendered output, a `[` outside a code span is always written `\[`. A `[` stays unescaped only inside a code span, which is either a span the author wrote on one line (row 1) or a span the renderer wrote around a token (`wrap`). A CommonMark renderer opens link, reference-link and image text only at an unescaped `[`, so no link, reference link or image can form from the value, whatever the rest of the value holds. The link and image rows (3 and 4) exist so that a link shows as typed inside a code span, as AC3 requires. The `\[` rule (row 12) is the safety net under them, and it is what makes the invariant hold even when the link rows are wrong about where a link ends. The invariant is checked by `TestRenderMarkdown_NoLiveLinkProperty` through an independent oracle (see "Test design"), and it was checked while writing this spec against two CommonMark renderers (see "Checked against CommonMark renderers").

Safety invariant for fences: in the rendered comment, every line outside a code fence starts with at most one space, and every fence the renderer keeps or closes was opened by a line with 0 or 1 leading space. In CommonMark such a line is always a top-level block. It can never be a continuation of a list item (a list item's content starts at column 2 or later) or of a block quote (which needs `>`), so a fence opened that way ends at its own closing line, and a closing line at column 0 closes it. A value whose fence-looking line is indented by 2 or more spaces is not kept as a fence; it is fenced as a whole (FR2), in a fence the renderer writes itself at column 0. This is what keeps the `**Remedy**` heading and the restart line outside every code block, and keeps links and HTML in a kept fence inside code. The invariant is checked by `fencesBalanced` wherever a test renders a whole comment and by `TestRenderMarkdown_FenceStructure`, and it was checked against the two renderers on the whole `RenderComment` layout (see "Checked against CommonMark renderers").

### `renderValue` algorithm

1. **Truncate.** `text, truncated := truncateRunes(s)` (2000 runes, on the raw value, before any escaping, so escaping never changes how much text is kept).
2. **Normalize.** Convert `\r\n` and `\r` to `\n`. Split into lines. Drop leading and trailing lines that are blank. A line is *blank* when it holds only spaces and tabs. Trim trailing spaces and tabs from every line. An empty result renders as the empty string.
3. **Classify lines (one pass, with fence state).** While scanning, track whether the line is inside a fence the value itself opens.
   - A fence opener is a line with **0 or 1** leading space (never a tab), then a run of 3 or more backticks or 3 or more tildes, then an optional info string. For a backtick fence the info string must not contain a backtick (so ```` ```foo``` ```` is inline code, not a fence). The opener records the fence character and its run length *n*.
   - A closer is a line with **0 to 3** leading spaces (CommonMark's closing rule), then a run of the same character with length of at least *n*, then only spaces and tabs. The closer rule is wider than the opener rule on purpose, see "Why an opener has 0 or 1 space and a closer 0 to 3".
   - A fence still open at the end of the value is *unclosed*.
   - A fence-looking line with 2 or more leading spaces, or a tab, that is outside a value fence is **not** an opener. It is an *indented line*: three backticks and `go` after two spaces, and a line of three backticks after three spaces, are indented lines. Fence detection runs first only for lines with 0 or 1 leading space.
   - Outside value fences, a non-blank line that starts with a tab or with two or more spaces (an indented line) marks the value *preformatted*. Lines inside a value fence, including its closer, never mark it preformatted.
4. **Preformatted value.** If the value is preformatted, the body is `fenced(text)`: one code fence around the whole (truncated, normalized) text, as today, and the algorithm continues at step 6 (it does not return here). `text` was already cut in step 1, so `fenced` adds no truncation note of its own; step 6 adds it. The fence is `max(3, longestBacktickRun(text)+1)` backticks, so a fence inside the text stays inside it. This is the Go stack trace and log excerpt case.
5. **Otherwise render segments in order.**
   - *Value fence segment*: the original lines, verbatim. If the fence is unclosed, append a closing line of *n* fence characters at column 0. This is what keeps a cut fence from swallowing the rest of the comment. The opener has 0 or 1 leading space, so it is a top-level block and the closing line at column 0 closes it.
   - *Text segment*: each blank line becomes an empty line. Each maximal sequence of consecutive non-blank text lines (a *run*, which is one Markdown paragraph) is joined with `\n` and passed to `renderRun` as one string. Runs are therefore scanned as a whole, so a construct that crosses a line break is seen. Newlines between non-blank lines are kept as single `\n`. GitHub renders a single newline in an issue comment as a line break, so no trailing spaces are added. Blank lines stay as paragraph separators. In a text run a line has at most one leading space (two or more would have made the value preformatted).
6. **Truncation note, on every path.** Steps 4 and 5 each produce a body. Whichever one ran (whole-value fence, or text and value-fence segments), if `truncated` from step 1 is true, append `\n_(truncated to 2000 characters)_\n` (blank line, then the existing note) to the body. The note comes after any closing fence, including the fence of a whole-value body.

The result always ends with `\n`. `RenderComment` keeps its existing `"\n**Actual**\n\n"` and `"\n**Remedy**\n\n"` separators, so a blank line always precedes the next heading.

**Why an opener has 0 or 1 space and a closer 0 to 3.** CommonMark lets a fence opener have up to 3 leading spaces, but a line indented 2 or 3 spaces right after a list item (`- `, `* `, `+ `, and for 3 spaces `1. `) belongs to that item. The fence then ends at the first later line that is indented less than the item, and fenced code has no lazy continuation. If the renderer kept such a fence as a value fence, its closing line at column 0 (step 5) would not close it. It would open a second fence that swallows `**Remedy**` and the restart line, and everything after an early end (a link, a mention, `<details>`) would act as live text. Example: the lines `- step`, a line of three backticks indented by two spaces, and `  go test ./...`, with the value ending there. A line with 0 or 1 leading space can never belong to a list item or a quote, so only those lines are openers. The closer needs the opposite care. In CommonMark a closing line with 2 or 3 spaces does close a fence. A scanner that only accepted 0 or 1 spaces would keep treating later lines as "inside the fence" and write them verbatim after the renderer had already closed it, which leaves them live. So the closer rule is CommonMark's 0 to 3. Both rules were checked against the two renderers (see "Checked against CommonMark renderers"): opener 0 to 3 (the earlier spec) swallowed the comment or left a link or HTML live in many cases, opener 0 or 1 with closer 0 or 1 still did, and opener 0 or 1 with closer 0 to 3 did not in any.

### `renderRun` (one paragraph: consecutive non-blank text lines joined with `\n`, outside any fence)

`renderRun` scans the run left to right. At each position it tries the rows below in order. The first that matches wins, the matched text is consumed, and scanning continues after it.

Three helpers define the matching rules the rows use. Tails A and B are not constructs of their own and are never tried at a position: they define the tail that rows 3 and 4 require after the closing `]`.

- `codeSpanEnd(run, i)`: `run[i]` starts a backtick run of *n* backticks. If a later run of exactly *n* backticks exists **on the same line**, return the index just after it. Otherwise return "none". A user code span never crosses a line break. A span the author wrote across lines is treated as stray backticks (row 2), which are escaped, so it shows as typed and its contents are still checked. This also means a block-level construct that would interrupt the paragraph in a real renderer (a list item, a heading) can never leave a stray backtick that pairs with a wrapper.
- `closeBracket(run, i)`: `run[i]` is `[`. Walk forward with depth 1. A backtick run with a `codeSpanEnd` is skipped as a unit, because in CommonMark a code span binds tighter than the brackets of link **text** (`[a` + backtick + `](u)b` + backtick is not a link). Any other rune that is `[` adds 1 to the depth and `]` subtracts 1. Backslash is an ordinary rune here, because `renderRun` writes every backslash outside code as `\\`, so no bracket in the output is escaped by the author's backslash. Line breaks are ordinary runes, so the text may cross lines. Return the index of the `]` where the depth reaches 0, or "none" at the end of the run. This is CommonMark's bracket-balanced link text (`[a [b] c](u)` is one link with text `a [b] c`).
- `tailEnd(run, k)`: `run[k]` is the rune right after the closing `]`. Returns the index just after the tail, or "none". `(` starts **Tail A** and `[` starts **Tail B**, both defined below the table. Any other rune gives "none".

| # | Construct | Match at the current position | Output |
|---|-----------|-------------------------------|--------|
| 1 | User code span | A backtick run that has a `codeSpanEnd` on the same line. | The span from the opening run to the closing run, verbatim. No escaping, no wrapping inside it. |
| 2 | Stray backtick run | A backtick run with no `codeSpanEnd`. | Each backtick as `` \` ``. |
| 3 | Image | `!` then `[` where `closeBracket` finds a `]` and `tailEnd` finds a tail after it. | `wrap(token)` for the whole image, `!` through the end of the tail. |
| 4 | Link | `[` where `closeBracket` finds a `]` and `tailEnd` finds a tail after it. This covers `[text](url)`, `[text][ref]` and `[text][]`. | `wrap(token)` for the whole link, `[` through the end of the tail. |
| 5 | Bare URL | Starts at `http://`, `https://` or `www.` (case-insensitive), and the previous rune is not a letter or digit. Runs to the next white space or `<`. Trailing `.,;:!?"')]}` are cut off the token and written as normal text after it. `www.` must be followed by a letter or digit. | `wrap(token)` |
| 6 | `GH-N` | `GH-` (case-insensitive) and 1 or more digits. The previous rune is not a letter, digit, `_` or `-`. The next rune is not a letter, digit or `_`. | `wrap(token)` |
| 7 | `owner/repo#N` | `[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+#[0-9]+`. The previous rune is not a letter, digit, `_`, `.`, `-` or `/`. The next rune is not a letter, digit or `_`. | `wrap(token)` |

| 10 | `<` | `<` | `&lt;` |
| 11 | `\` | `\` | `\\` |

This is every `[` in the run that is not the start of a wrapped link or image and not inside a user code span: link text with no tail, a shortcut reference `[text]`, a `[` that starts a definition line (`[ref]: url`, `[^1]: note`, including one inside a blockquote or list item), a task-list `[ ]`, and the outer `[` of a nested pair whose own tail was not found. | `\[` |
| 13 | Anything else | any other rune, including a `!` that is not followed by a matching link | itself |

**Tail A: inline tail** (the rune after `]` is `(`; `k` is its index). Look for the end of the tail in this order. Code spans are **not** skipped anywhere in a tail: a backtick is an ordinary rune. CommonMark reads the destination and title in `(...)` as plain text, so a backtick there can pair with a later backtick on the line and must not hide the `)` (the destination of `[a](u` + backtick + `)b` + backtick is `u` + backtick, and the link is live).

1. *Depth scan.* Start at depth 1 just after the `(`. `(` adds 1 and `)` subtracts 1. The tail ends just after the `)` where the depth reaches 0. Line breaks are allowed. A `<` that is the first non-space rune after the `(` starts a destination that ends at the next `>` (parentheses inside it do not count). A `"` or `'` that follows white space starts a title that ends at the next same quote (parentheses inside it do not count). A `<`, `"` or `'` with no end is an ordinary rune. Backslash is an ordinary rune.
2. *Fallback.* If the depth scan reaches the end of the run without closing, the tail ends just after the first `)` that follows the `(`. This keeps the match a superset of what CommonMark reads. CommonMark honours a backslash escape that step 1 does not: in `[` newline `](` + backtick + `\()` + backtick + `a` the `\(` does not count, so `)` closes the link, while the depth scan sees two opening parentheses. markdown-it 14.3.2 and micromark 4.0.3 both make this a link, and a depth-only matcher left it live.
3. *No match.* If the run has no `)` after the `(`, there is no tail.

So Tail A is found if and only if a `)` follows the `(` in the run. A token wrapped through the first `)` (step 2) or the balanced `)` (step 1) always contains the `[` and the `(`, so the link opener is inside code either way. Text after the wrapped token is scanned on its own.

**Tail B: reference tail** (the rune after `]` is `[`). The tail ends just after the next `]` (this label cannot hold brackets). `[]` is allowed. If there is no next `]` in the run there is no tail.

Rows 3 and 4 are tried before the URL, reference and mention rows, so a link whose text holds a URL, `#12` or `@bob` is wrapped once as a whole. Because `[` is reached left to right, the outermost balanced link wins. When the outer `[` has no match (no balanced `]`, or no tail), row 12 writes it `\[` and scanning continues, so `[a [b](u)` gives `\[a ` followed by the wrapped `[b](u)`. When rows 3 and 4 match a span that CommonMark would split (`[a [b](u) c](v)`, where the inner link is the real one), the whole span is wrapped. Over-wrapping is harmless, because wrapped text shows as typed.

**Why row 12 escapes every remaining `[`.** A single left-to-right pass cannot see that wrapping an inner token changes how the outer brackets pair. Example: `[[](!])x](y)`. The outer `[` closes at the `]` inside the inner destination `(!])`, and the next rune is `)`, so the outer `[` has no tail. The inner `[](!])` is wrapped, which hides that `]` in code. In the output, the outer `[` now closes at the `]` of `x](y)`, which has a tail. If row 12 wrote the outer `[` as itself, CommonMark would render `<a href="y">` (markdown-it 14.3.2 and micromark 4.0.3 both do). Writing it `\[` leaves no unescaped `[` outside code, so the class cannot occur. This also settles shortcut references and definitions: a shortcut reference `[text]` and a definition line are literal text, because their `[` is escaped, in every block context (top level, blockquote, list item). The text still shows `[` on GitHub, so it reads as typed.

**`wrap(token)`.** If the token has no `\n`: let *k* = `longestBacktickRun(token) + 1`, write *k* backticks, the token, *k* backticks. If the token starts or ends with a backtick, put one space inside each side (`` `` x` `` ``), because Markdown strips one space from each side. A token that holds a backtick (the destination `u` + backtick in `[a](u` + backtick + `)`) gets a longer wrapper by this rule.

**A token with line breaks (links and images only).** A code span does not keep a line break, because a renderer turns it into a space, and a bracket left outside a span would stay live. So the token is split at each `\n` and every piece is wrapped separately with the rule above. A piece's leading space (a line can start with one space) is written before its opening backticks, outside the span. The `\n` between pieces is written as it is, so the line break stays a line break. Every `[` and `]` of the token ends up inside one of the pieces' spans, and no piece is empty or blank, because a run has no blank lines and the token starts with `[` or `!` and ends with `)` or `]`. Example: `[a` newline `b](https://x.y)` becomes `` `[a` `` newline `` `b](https://x.y)` ``.

**Adjacent backticks.** Two backtick runs that touch merge into one longer run and break pairing. So if the output so far ends with a backtick, write one space before a `wrap(...)` (before the first piece). If the next input rune is a backtick, write one space after it (after the last piece). (This makes two adjacent tokens come out as `` `[a](b)` `[c](d)` ``.)

**Why backslash and stray-backtick escaping is part of this design.** Without it a stray backtick in a value would pair with the backtick of a wrapper and expose the token (breaking AC3). A backslash before a character is consumed by Markdown, so Go `%q` text such as `\"` would show without its backslash, `\<` would show `&lt;`, and `\[a](u)` would show `[a](u)` as a live link only if the `\` were dropped. Escaping `\` as `\\` outside code makes the text show as typed, keeps the `` \` `` escape unambiguous, and is why `closeBracket` can treat backslash as an ordinary rune.

**What is deliberately not touched:** `&` (an entity such as `&amp;` shows as the character; it cannot act), `>` (a leading `>` is a quote, which is Markdown text), emphasis, lists and headings the value writes, e-mail addresses and commit SHAs (the issue lists neither). Formatting that depends on a `[` loses its effect: a task-list `- [ ] x` shows as the text `[ ] x` and not as a checkbox. That is the cost of row 12 and is accepted, because a checkbox is not a feature the issue asks to keep and the values are error messages.

### Interpretations of the issue text (recorded so the validator and reviewers can judge them)

None of these narrows the issue. Each fills a gap in the issue's wording. They are not spec deviations.

1. **Blank means spaces and tabs only.** "any line that starts with a tab or two or more spaces" would otherwise send `a\n  \nb` (a whitespace-only line used as a paragraph break) to a code fence. Whitespace-only lines are treated as blank lines.
2. **A fence is "kept as it is" when its opener has 0 or 1 leading space.** Fence detection precedes the indentation test only for such lines. Lines inside a value fence never count as indented. A fence-looking line indented by 2 or 3 spaces is an indented line, so FR2 puts the whole value in one fence: `"- a\n  ```\n  x"` and `"a\n   ```\nx\n```"` each come out as one 4-backtick fence around the whole value. The reason is in "Why an opener has 0 or 1 space and a closer 0 to 3": a fence indented that way can belong to a list item, and a real renderer ends it early. This also reads FR2 literally ("any line that starts with a tab or two or more spaces"). A closing line may still have up to 3 leading spaces, because that is how a renderer closes a fence.
3. **Whole-value fencing.** "is placed in a code fence, as today" is read as: the entire value goes in one fence, not only the indented lines. A value that has both its own fence and an indented line outside it is fenced as a whole, in a fence longer than any backtick run it contains.
4. **Tilde fences** are fences too, and an unclosed one is closed. This keeps a cut value from swallowing the rest of the comment.
5. **`[text][]`** counts as a reference link. **Definition lines** (`[ref]: url`, including a label that spans lines, and one inside a blockquote or list item) and shortcut references (`[text]`) are neutralized by escaping their `[` (row 12). They are not on FR3's list of tokens to wrap. They are escaped because a definition hides its line and could turn a later `[text]` into a live link, and a `[` outside code is what a link needs to start. The text still shows as typed.
6. **Escapes** for stray backticks, backslashes and an unmatched `[`, and the **space between touching backtick runs**, are required by Functional Requirement 3 ("show as typed" and "have no effect") and are described above.
7. **A link's tail is read as CommonMark reads it, not as code.** In `[text](url)`, the `(...)` is not subject to code spans, so a backtick inside it is an ordinary rune (Tail A). This is why "including a token that contains a backtick" in AC3 covers a backtick in the destination as well as in the link text.
8. **Links and images are matched across the whole paragraph.** "Markdown links `[text](url)` and reference links `[text][ref]`; images `![alt](url)`" is read as CommonMark links: bracket-balanced text, which may hold brackets and line breaks. A token that crosses a line break is wrapped in one code span per line, so that the line break is kept and no bracket is left outside code.

### Checked against CommonMark renderers

The rules above were prototyped in two scratch Go programs and each output was rendered with two CommonMark implementations, markdown-it 14.3.2 (`commonmark` preset, HTML off) and micromark 4.0.3 (core, no extensions). Neither is GitHub's renderer (cmark-gfm), and neither was available with GFM extensions, so GitHub-only constructs (mentions, `#N`, autolink literals) are covered by their own rows and not by this check. The prototypes are not part of the change. The first covers the text path (`renderRun`, `codeSpanEnd`, `closeBracket`, Tails A and B, `wrap`). The second adds the fence scanner, whole-value fencing, the closing line of an unclosed fence, truncation and the whole `RenderComment` layout (marker, intro, list, headings, default remedy, restart line), and was written for round 4.

- **Inputs.** About 3.9 million strings: every string of length 1 to 5 over `[ ] ( ) ! \ backtick a newline`, and seeded random strings of length 6 to 24 over several alphabets that add quotes, `<`, `>`, `#`, `-`, `1.`, `=`, `*`, `_`, `~`, `@`, `http:/` and spaces (so blockquote, list, heading and setext lines occur). Strings with a value fence or only white space were skipped.
- **Result for the rules in this spec.** Zero outputs contain an `<a` or `<img` in either renderer. The independent `hasLiveLink` oracle returned false on every output. On the inputs, the oracle returned true for every string that micromark turns into a link (apart from `<...>` autolinks, which cannot occur in an output because `<` is written `&lt;`).
- **What the check found, and what changed because of it.** (1) The validator's finding: with Tail A skipping code spans, `[a](u` + backtick + `)b` + backtick and `[t](https://x.y/a` + backtick + `b) see ` + backtick + `code` + backtick stayed live (`<a href="u%60">`, `<a href="https://x.y/a%60b">`). Tail A now treats a backtick as an ordinary rune. (2) With that fixed, a backslash before a parenthesis inside a verbatim code span, `[` + newline + `](` + backtick + `\()` + backtick + `a`, still produced a link, because CommonMark honours `\(` as an escape and the depth scan does not. Tail A now falls back to the first `)`. (3) The re-pairing case `[[](!])x](y)` (a single pass cannot see that wrapping an inner token re-pairs the outer brackets) produced `<a href="y">`. Row 12 now escapes every unmatched `[`.
- **Fence scanner and whole layout (round 4).** The second prototype was run on the whole comment, with the value as Actual (and as Expected, which also fills the default remedy). ## Test design (TDD, per AGENTS.md)

All new tests drive `RenderComment` (black box). They must compile against the current code and fail on their assertions, so the red run fails "for the expected reason" (the Expected/Actual section is still in a code fence, `<` is not escaped, and so on), never from a compile error. Do not call `renderValue` from a test.

Test helpers (in `render_test.go`):

- `section(got, name)`: the text between `**<name>**\n\n` and the next heading line, with the final newline removed. For `Expected` the end is the first `\n**Actual**\n\n` after the start. For `Actual` it is the first `\n**Remedy**\n\n`.
- `outsideFences(s)`: `s` with every fenced region removed. A line scan with the same rules as step 3: an opener has **0 or 1** leading space, then 3 or more backticks or tildes (a backtick opener's info string holds no backtick); a closer has 0 to 3 leading spaces, then a run of the same character at least as long as the opener's, then only spaces and tabs; a region that never closes runs to the end of `s`. A fence-looking line with 2 or more leading spaces is not an opener here either, so it stays in the result, where `hasLiveLink` and the `<` checks see it.
- `fencesBalanced(got)`: for a whole comment rendered with an empty or plain-text remedy, true only when all three hold: (1) the line scan above ends outside any fence; (2) **no line outside a fence starts with a tab or with two or more spaces** (this is the condition that keeps every kept or closed fence a top-level block in a real renderer, see "Why an opener has 0 or 1 space and a closer 0 to 3"; the helper does not rely on the implementation's own reading of an indented fence line); (3) the lines `**Expected**`, `**Actual**` and `**Remedy**` and the line that starts `To restart this issue` are each outside every fence. Before this rule a helper that used the implementation's own 0-to-3 rule passed the cases a real renderer swallowed. A prototype of the helper flagged 3,331 of 20,000 sweep values when the renderer used opener 0 to 3, and none with the rules of this spec.
- `fixture419(t)`: reads `testdata/punchout-419-actual.txt` with `os.ReadFile`, removes one trailing `\n` if present, and fails the test unless the text has exactly 1,886 runes (which is under the 2,000 cut, so it is never truncated), contains no `\n`, and has the SHA-256 recorded above. A bad copy therefore fails with a clear message.
- `hasLiveLink(s)`: an independent oracle for "would a CommonMark renderer turn something here into a link". It is written from CommonMark's rules, not from the renderer's rows, and it is deliberately looser than the renderer: it reports true whenever a link is possible. For each paragraph of `s` (split at blank lines): **(1) Find the openers and the closing `]` of the link text.** Walk the runes. A `\` and the rune after it are both literal, and that rune is never a bracket or a backtick. A backtick run of length *n* that has a later run of exactly *n* backticks anywhere in the paragraph (a CommonMark code span may run over a line break) is dropped together with everything between the two runs. Other backticks are literal. For each unescaped `[` that is left, find its bracket-balanced `]` in what remains (nested unescaped brackets count, across line breaks). **(2) Look for the tail in the paragraph text itself, without dropping code spans and without honouring escapes.** If the rune after that `]` is `(`, the opener is live when a `)` occurs anywhere later in the paragraph. If it is `[`, the opener is live when a `]` occurs anywhere later. Return true if any opener is live. Code spans are dropped only in step 1 because they bind tighter than the brackets of link text, but they do not apply inside the `(...)` destination, so step 2 reads the raw text. `[a][b]` counts as live even though it needs a definition to be a link, because a definition could exist. The oracle is applied to `outsideFences(section)`. Its rules were checked against micromark 4.0.3 and markdown-it 14.3.2 (see "Checked against CommonMark renderers"): on the strings listed in `TestRenderMarkdown_LiveLinkOracle` it agrees with micromark, except `[a][b]`, where it is stricter on purpose.

### Exact rows for tails, escaped brackets and definitions

Each pair is a Go interpreted string literal for the Expected value (`in`) and for the exact Expected section (`want`, without the final newline). `\\` is one backslash, `\n` is a newline and a backtick is a backtick. They are the `want` values for `TestRenderMarkdown_RawTokens`, `TestRenderMarkdown_RawTokensWithBackticks` and `TestRenderMarkdown_DefinitionLines`. Each was produced by a prototype of the rules above and then rendered with markdown-it 14.3.2 (commonmark preset) and micromark 4.0.3: none of the `want` strings contains a link or an image, and the text shown is the `in` text. Where a pair seems to disagree with the prose, the prose is wrong and the pair is the contract. Do not change a `want` to make the implementation pass; report the disagreement in the sentinel.

```text
// A backtick in the tail (Tail A does not skip code spans)
in:   "[a](u`)b` c"
want: "``[a](u`)``b\\` c"
in:   "[t](https://x.y/a`b) see `code`"
want: "``[t](https://x.y/a`b)`` see `code`"
in:   "[a](u`)"
want: "``[a](u`)``"
in:   "[a](u`b`)"
want: "``[a](u`b`)``"
in:   "[a](<u`v>) `x`"
want: "``[a](<u`v>)`` `x`"
in:   "[a](b\\()x"
want: "`[a](b\\()`x"
in:   "[a](u \"x)y\")"
want: "`[a](u \"x)y\")`"

// A backtick in the link text still hides the tail (code spans bind tighter than link text)
in:   "[a`](u)b`"
want: "\\[a`](u)b`"

// Unmatched [ is escaped (row 12), including the re-pairing case
in:   "[[](!])x](y)"
want: "\\[`[](!])`x](y)"
in:   "![[](!])x](y)"
want: "!\\[`[](!])`x](y)"
in:   "[#12]"
want: "\\[`#12`]"
in:   "[a [b](u)"
want: "\\[a `[b](u)`"
in:   "a [b] c"
want: "a \\[b] c"
in:   "x ![a"
want: "x !\\[a"
in:   "- [ ] todo"
want: "- \\[ ] todo"

// Definition lines and shortcut references (row 12)
in:   "[ref]: https://x.y"
want: "\\[ref]: `https://x.y`"
in:   "[^1]: note"
want: "\\[^1]: note"
in:   "[foo\nbar]: https://x.y"
want: "\\[foo\nbar]: `https://x.y`"
in:   "> [x]: u"
want: "> \\[x]: u"
in:   "- [x]: u"
want: "- \\[x]: u"

// Backslash before a link
in:   "\\[a](u)"
want: "\\\\`[a](u)`"
```

What these pairs show, in CommonMark terms: in the first group the `)` closes the link even though a backtick sits in the destination, so the whole link is wrapped and a later lone backtick is escaped (the trailing `\` plus backtick in the first `want`). In the second group the backtick in the link **text** pairs with the later backtick, so `](u)b` is inside a code span and nothing is a link, and the `[` is escaped. In the third group `[[](!])x](y)` is the re-pairing case: only the inner `[](!])` is wrapped and the outer `[` is escaped, so `x](y)` cannot close it.
